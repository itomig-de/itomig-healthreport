Neue iTop-Klassen der Extension „itomig-healthreport"

HealthcheckRun, HealthcheckModuleReport & HealthcheckUpload – Datenmodell und Funktionsweise

Die Extension itomig-healthreport ergänzt das iTop-Datenmodell um drei neue Klassen, um Healthcheck-Auswertungen dauerhaft als iTop-Objekte zu speichern statt nur als Dateien auf der Platte. Damit bekommt jeder Lauf eine Historie, eine Detailseite, Such-/Listenansicht und Zugriffskontrolle direkt über iTop. Seit Version 26.3.0 kommt HealthcheckUpload hinzu: der Eingangs-Briefkasten für ZIPs, die Kunden selbst über das Portal hochladen, bevor ITOMIG sie auswertet.
HealthcheckUpload n → 1 HealthcheckRun 1 → n HealthcheckModuleReport

Klasse: HealthcheckRun

Ein ausgewerteter Healthcheck-Lauf

DB-Tabelle: itomig_healthreport_run

Repräsentiert genau einen ZIP-Upload: Kunde, Umgebung, Zeitpunkt, Versionen sowie das Gesamtergebnis über alle Module hinweg (Ampel + Anzahl ausgewerteter Module). Das Original-ZIP und das Management-Summary liegen als Datei-Anhänge (Blobs) direkt am Objekt.

FeldTypBedeutung
kundeStringKundenname aus dem manifest.json des ZIPs
umgebungStringUmgebung (z. B. Produktion, Test)
zeitpunktDateTimeZeitpunkt der Datensammlung beim Kunden
itop_versionStringiTop-Version der Kundeninstanz
db_server_versionStringDB-Server-Version der Kundeninstanz
extension_versionStringVersion der Collector-Extension itomig-healthcheck
ampel_gesamtEnumrot / gelb / grün – höchste Ampel aller Module
modul_anzahlIntegerAnzahl erfolgreich ausgewerteter Module
zip_dateiBlobOriginal-Upload (zur Nachvollziehbarkeit/Re-Auswertung)
summary_htmlBlobManagement-Summary als fertiges HTML
summary_jsonBlobManagement-Summary als JSON (maschinenlesbar)
modul_reportsLinkedSetAlle zugehörigen HealthcheckModuleReport-Objekte (Tab auf der Detailseite)

Klasse: HealthcheckModuleReport

Der Report eines einzelnen Moduls innerhalb eines Laufs

DB-Tabelle: itomig_healthreport_modul

Für jedes der 9 ausgewerteten Module (Design, Daten, Synchro, Integration, System, Datenschutz, Tabellen-Übersicht, Spalten-Befüllung, Objekt-Aktualität) entsteht pro Lauf genau ein HealthcheckModuleReport, verknüpft mit seinem HealthcheckRun über den Schlüssel run_id.

FeldTypBedeutung
run_idExternalKeyVerweis auf den zugehörigen HealthcheckRun (Löschen des Laufs löscht auch seine Modul-Reports)
kategorieStringInterner Kategorie-Schlüssel, z. B. system, design
labelStringSprechender Anzeigename, z. B. „Server- & Systemzustand"
ampelEnumrot / gelb / grün – höchster Schweregrad der Befunde dieses Moduls
befund_anzahlIntegerAnzahl gefundener Befunde in diesem Modul
report_htmlBlobVollständiger Detail-Report als HTML
report_jsonBlobDetail-Report als JSON

Klasse: HealthcheckUpload

Ein von einem Kunden über das Portal hochgeladenes ZIP, noch nicht ausgewertet

DB-Tabelle: itomig_healthreport_upload

Eingangs-Briefkasten für Portal-Uploads: legt nur das ZIP samt Metadaten ab (status = „Neu"). Bewusst getrennt von HealthcheckRun, weil dessen Pflichtfelder (Ampel, Modul-Anzahl, Zeitpunkt der Datensammlung) erst aus der Auswertung entstehen und beim Portal-Upload noch nicht bekannt sind. Erst wenn ITOMIG in der Konsole „Auswerten" klickt, entsteht daraus ein HealthcheckRun – der Portal-Upload selbst löst keine Auswertung aus.

FeldTypBedeutung
org_idExternalKeyOrganisation (Kunde) des angemeldeten Portal-Kontakts
hochgeladen_von_idExternalKeyPerson, die den Upload durchgeführt hat
eingegangen_amDateTimeZeitpunkt des Portal-Uploads
dateinameStringOriginal-Dateiname des hochgeladenen ZIPs
zip_dateiBlobDas hochgeladene ZIP selbst
statusEnumneu / ausgewertet / fehler
run_idExternalKeyVerweis auf den daraus erzeugten HealthcheckRun (erst nach Auswertung gesetzt)
fehlermeldungTextFehlertext, falls die Auswertung fehlgeschlagen ist

Wie die Objekte entstehen

  1. Ein Admin lädt im iTop-Menü „Healthcheck → Healthcheck hochladen" ein Collector-ZIP hoch – oder ein Kunde lädt es selbst über die Portal-Brick „Healthcheck hochladen" hoch (dann entsteht zunächst nur ein HealthcheckUpload, siehe unten).
  2. Beim Admin-Upload reicht der Controller (HealthReportController) die Datei sofort an ReportPipeline weiter. Diese bindet die bestehende, iTop-unabhängige Auswertungs-Engine (lib/, reporters/) ein, entpackt das ZIP und lässt jedes enthaltene Modul auswerten.
  3. RunPersister nimmt das Ergebnis der Pipeline und legt daraus ein HealthcheckRun-Objekt sowie je Modul ein HealthcheckModuleReport-Objekt an – inklusive aller Blobs (ZIP, Summary, Detail-Reports).
  4. Der Admin wird automatisch auf die Detailseite des neuen HealthcheckRun weitergeleitet. Dort zeigt iTop nativ alle Felder, die Ampel-Übersicht sowie einen Tab mit allen HealthcheckModuleReport-Objekten. Reports lassen sich direkt aus den Blob-Feldern im Browser öffnen.
  5. Über das Menü „Healthcheck → Healthcheck-Läufe" lässt sich jederzeit die komplette Historie aller ausgewerteten Läufe durchsuchen.

Portal-Upload durch Kunden

  1. Ein Kunde lädt im Portal über die Brick „Healthcheck hochladen" sein Collector-ZIP hoch. Der Portal-Controller (HealthReportUploadBrickController) legt daraus lediglich ein HealthcheckUpload mit Status „Neu" an – es findet keine Auswertung statt.
  2. ITOMIG sichtet eingegangene Uploads in der Konsole unter „Healthcheck → Eingegangene Uploads" und stößt die Auswertung dort gezielt per Klick auf „Auswerten" an.
  3. UploadProcessor nutzt dabei dieselbe ReportPipeline/RunPersister-Kette wie der Admin-Upload und erzeugt so ganz normal einen HealthcheckRun. Anschließend wird der Upload auf Status „Ausgewertet" gesetzt und über run_id mit dem neuen Lauf verknüpft (oder auf „Fehler" mit Fehlertext, falls die Auswertung scheitert).
  4. Ohne installiertes Portal (itop-portal-base) bleibt die Extension unverändert nutzbar – die Portal-Bestandteile schalten sich nur zu, wenn das Portal vorhanden ist.
